# ADR-0002：评测分层以设计文档（32 号）为准

- 状态：已接受
- 日期：2026-09-22

## 背景

两处文档对「评测三层体系」给出了**互不兼容**的定义。经逐字核对，二者不是同一体系的不同命名：

**00 号 §3.2（总体开发方案）**

| 层级 | 内容 | 通过标准 | 运行时机 |
| --- | --- | --- | --- |
| L1 单元 | 纯函数逻辑 | ≥95% | pre-commit hook |
| L2 集成 | API 端点行为（结构、状态码、认证） | ≥90% | 每个工具组完成 |
| L3 质量 | AI 内容质量（含辅导安全性） | ≥70% | 每日收工、push 前 |

**32 号 §1.3、§五（评测体系设计）**

| 层级 | 判定方式 | 触发频率 | 场景数 |
| --- | --- | --- | --- |
| 基线层 | 代码可精确断言 | 每次 commit | 60 |
| 边界层 | 多数可精确断言 | 每次 commit | 24 |
| 回归层 | 精确断言 + LLM 评分 | 每次 PR / 发版前 | 25 |

冲突点（逐条核实，非推测）：

1. **阈值对不上**。32 号全文不存在 90% 和 70%。它的门禁是：安全层 100%（不可降级）、路由层 ≥85%、质量层 ≥3.5/5 平均分、性能层 P95 达标。
2. **覆盖内容对不上**。00 号 L2 的「API 端点层」在 32 号三层里**没有对应层**——32 号的三层按「判定方式 / 成本 / 频率」划分，不按测试类型划分。
3. **归层相反**。「辅导安全性」在 00 号属 L3 质量层，在 32 号属**基线层**（安全隔离 16 场景）且阈值 100%。
4. **时机对不上**。00 号的「每个工具组完成」「每日收工」两个触发点在 32 号中不存在。
5. **记号不存在**。32 号全文没有 `L1`/`L2`/`L3` 这三个层级记号（仅在 mermaid 图中出现节点 ID `BL1`–`BL4`）。
6. **规模对不上**。00 号写「100 条 Golden 数据集」，32 号是 **109 个评测场景**。Golden 数据集是贯穿三层的场景全集，**不是第三层**。
7. **32 号自身还有第四套命名**。其 §八 CI 门禁用 P0/P1/P2 + 安全层/路由层/质量层/性能层，与前两套都不同。

## 决策

1. **阶段五（Evals 体系）的实现以 32 号为准**。分层名称、场景划分、通过标准、触发时机全部采用 32 号。
2. **Golden 数据集是 109 个场景**，不是 100 条。它是数据资产，不是评测层级。
3. **`CLAUDE.md` 工具链表保留 00 号的 L1/L2/L3 字样**，因为那张表描述的是**工作流的层序**（思考→规格→实现→质量→流程→骨架），与评测技术实现是两回事；但 L1/L2/L3 **不得**被当作通过阈值的依据。
4. **`baseline.json` 是实现细节**。00 号 §3.3 用它做劣化比对，32 号未定义该文件。阶段五落地时自行确定格式与命名。
5. 32 号的「双轨」（确定性 92 场景 / LLM-as-Judge 17 场景）与「三层」是**同一批 109 场景的两种正交切法**，不是两套体系。

## 影响

- `CLAUDE.md` 的「质量标准（Evals）」小节按 32 号重写，并标注 00 号的 L1/L2/L3 仅为教程叙述口径。
- `CLAUDE.md` 的 Git 门禁一行引用了 `baseline.json`——保留，但注明该文件名待阶段五确定。
- 阶段五动工前必须重读本 ADR。若届时决定改用 00 号口径，本 ADR 需先被取代。
