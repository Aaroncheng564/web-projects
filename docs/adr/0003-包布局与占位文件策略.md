# ADR-0003：Python 包布局与占位文件策略

- 状态：部分待定（待阶段一「环境搭建」裁决）
- 日期：2026-09-22

## 背景

`chemai-backend/` 的目录骨架已建（59 个目录，41 个 `.gitkeep`），但没有 `__init__.py`。这不是疏漏，是刻意的。根级 `requirements.txt` 已于 2026-09-22 依赖清单确定后创建，理由与钉版见第 2 条。

同时存在一个未决的架构问题：`chem_skills/` 的语义。

## 决策

### 已定

1. **`app/` 与 `agent/` 是普通 Python 包**，阶段一为每个子包补 `__init__.py`。二者平级：`app/` 承载业务（models / api / services / schemas / middleware / utils），`agent/` 承载 Agent 编排（tools / channel / prompts）。

   > 注：课程已有骨架把 Agent 放在 `app/agents/`。本项目将其提升为顶层 `agent/`，是**有意的结构差异**，不是错误。

2. **骨架提交不建空 `requirements.txt`**。30 号 §20.2 规定每个 `chem_skills/` 子目录带 `requirements.txt`，但**该文件在其依赖真正确定时创建**（即该技能开始实现时），不预先建占位。空的 `requirements.txt` 会让后来者误以为依赖已梳理过，比没有更糟。

   根级 `chemai-backend/requirements.txt` 是这条规则的第一个落地实例：骨架阶段不建，2026-09-22 依赖清单确定后才建。它额外钉了两项**实测必需**的约束——不加则项目起不来：

   | 钉版 | 不钉的后果（已实测，非推测） |
   | --- | --- |
   | `numpy<2` | chromadb 0.4.22 在 import 期求值 `np.float_`，该别名已在 NumPy 2.0 移除 → `AttributeError`，`import chromadb` 直接失败（实测 numpy 2.4.6 崩、1.26.4 正常） |
   | `bcrypt==4.0.1` | passlib 1.7.4 停更于 2020，其 bcrypt 后端初始化时用超长口令自检；bcrypt 5.0 把静默截断改成抛异常 → `ValueError: password cannot be longer than 72 bytes`（实测 5.0.0 崩、4.0.1 正常） |

   两条钉版写在文件末尾的「兼容性钉版」注释块里，带实测版本对照。**不要当成冗余清掉**——它们不是版本洁癖，是让上面那两行约束能真正 import 的前提。

   > **编码坑（已踩，勿重踩）**：`requirements.txt` 里的中文注释必须让文件以 PEP 263 声明开头——首行写 `# -*- coding: utf-8 -*-`。pip 用 `auto_decode` 读该文件，在中文 Windows（GBK 区域）下，**既无 BOM 又无编码声明时会回退到 GBK**，UTF-8 中文字节直接抛 `UnicodeDecodeError: 'gbk' codec can't decode byte 0xae`。实测：不加声明 → 报错；加声明 → 正常。
   >
   > 这个坑的危险之处在于**它只在本地复现**：GitHub Actions 的 ubuntu runner 与 `python:3.11-slim` 都是 UTF-8 区域，CI 全绿而开发者本机 `pip install` 失败，很容易被误判成「环境问题」而不是文件问题。备选方案是存成 UTF-8 with BOM，pip 也认；但若将来有工具不剥 BOM，第一条依赖会变成 `﻿fastapi==0.109.2` 而被静默污染，故取声明式而非 BOM。

3. **`.gitkeep` 只用于保留空目录**。判据：该目录下没有任何已跟踪文件，**且**没有任何已跟踪文件的路径以它为前缀。两条同时成立才留着，否则删掉。

   推导：git 只跟踪文件、不跟踪目录。只要目录下任一层存在 `.gitkeep`，git 就会在检出时连带建出整条路径上的所有父目录。因此**父目录不需要自己的 `.gitkeep` 来留住自己**。举例说明这个坑：

   - `chem_skills/chemistry_memory/` 曾同时有 `.gitkeep`、`engine/.gitkeep`、`prompts/.gitkeep`。后两者已足够让 `chemistry_memory/` 在检出时出现，父目录那份是纯冗余，已删除（`notification` / `improvement` 同理）。
   - 其余 7 个技能从一开始就只在 `engine/` 与 `prompts/` 放 `.gitkeep`，没有父目录副本——这是**正确的形态**，新增技能时照此办理。
   - 例外的必要性来自 `.gitignore`：`data/chromadb/` 需显式保留 `.gitkeep` 并配 `!.gitkeep` 反忽略规则，因为该目录内容被整体忽略。这不是冗余，不要顺手删。

### 待定（阶段一裁决）

4. **`chem_skills/` 是否为可导入的 Python 包？** 两种可能：

   | 方案 | 含义 | 依据 |
   | --- | --- | --- |
   | A. 普通子包 | `chem_skills/` 是 `chemai_backend` 下的一个包，各技能 `import` 使用 | 结构简单，与 `app/`、`agent/` 一致 |
   | B. 插件目录 | 各技能是运行时动态加载的独立模块，不参与静态导入 | 30 号 §20.2 给**每个技能**配 `requirements.txt`，暗示它们有各自独立的依赖边界 |

   **倾向 A**。理由：单进程 FastAPI 应用不会在运行时为 10 个技能分别 pip 安装依赖；per-skill `requirements.txt` 更合理的解释是「记录该技能需要什么」，安装时取并集。方案 B 的理由不足以支撑插件化带来的复杂度。

   裁决前不要写任何 import `chem_skills` 的代码。

## 影响

- 阶段一必须先读本 ADR，先裁决第 4 条，再动手建包。
- 在裁决之前，`app/` 与 `agent/` 可以先按第 1 条补齐 `__init__.py`——这两条无争议。
- 「不建空文件」是本项目的一贯策略，后续遇到类似占位（如空的 prompt 模板、空的配置文件）沿用同一判断。
